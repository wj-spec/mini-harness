# Agent 实验台实施路线图

> 版本：v2，2026-11-08。状态：规划方案已复核；P1–P7 均未实施。
>
> [整体设计](design.md) · [任务与评审记录](task-log.md)

## 概览

推荐顺序：**可信运行证据 → SWE-bench 对照 → Terminal-Bench 对照 → 真实失败转回归 → 本地阅读工作台 → 基线与门禁 → 可选观测集成**。
这条路线服务于当前 coding 可靠性、W0 可复现起点和已有评测扩题，不新增 W0–W7 的已完成声明，也不替代正在推进的 Ink UX 切片。

**近期只细化 P1/P2**：P1 能独立解释一次任务，P2 以 SWE-bench 为首个主基准比较一次改动，复用已有 Harbor 与官方评分链路。Terminal-Bench 是紧随其后的必需阶段，不属于可选扩展。案例提取、Web 信息架构、门禁阈值需要前两阶段的真实数据才能细化。每阶段一个内聚结果，先验收再推进；没有投入时长基线，不承诺日历日期。

| 阶段 | 独立结果 | 对应需求 | 状态 |
|---|---|---|---|
| P1 运行证据包 | 实际运行身份与证据可查询、可验证、可解释缺失 | R1/R2 | 五节细化，待实施规格 |
| P2 SWE-bench 对照 | 固定 Verified 题集和官方 grader 比较两个候选 | R3/R8 | 五节细化，依赖 P1 |
| P3 Terminal-Bench 对照 | 固定版本的 Harbor 任务/试次、原生评分与对照 | R3/R8 | 必需阶段，目标与补细条件 |
| P4 失败转回归 | 一个真实失败变成可维护案例与新题集版本 | R4 | 目标与补细条件 |
| P5 本地实验工作台 | 运行、对比、案例和实验可以交互阅读 | R6 | 目标与补细条件 |
| P6 基线与回归门禁 | 采用决定有证据、回归可定位、旧基线可恢复 | R5 | 目标与补细条件 |
| P7 可选观测集成 | 按实际需要增加观测后端与其他评测适配 | R7 | 可选方向 |

## P1 · 可信运行证据包

**原型反馈输入（待纳入实施规格）**：用户优先诊断真实任务的失败、反复和高消耗，见 [业务旅程](business-workflows.md)。
P1 的证据包与只读查看应先验一条“任务结果 → 请求/工具/上下文 → 诊断依据”的真实路径；重点核对 task/segment/run/request 的显式关联，分别表达完整正文、内容指纹、估算占用与实际 usage。
诊断主路径已用历史产物做离线原型，但不替代生产采集验收；本增量不把正式 Web 提前列为 P1 交付。

### 前置条件

- [ ] 核查当前工作树与运行入口；保存已有未提交工作的身份，不混入本阶段改动。
- [ ] P1 change 冻结证据 schema、生产端与消费者兼容夹具、实际源码/配置的快照边界。
- [ ] 测量固定 10 万事件夹具的读取基线，在实现前锁定耗时、内存与采集开销门槛。
- [ ] 明确每个写入/快照操作的现有 Gate 或内部存储授权路径；新增执行能力不得绕过 ApprovalGate。

### 目标

对一个 Ink/stdio 日常任务导出可核查证据包，通过只读命令或报告查看实际运行身份、动作、最终验证与缺失材料。
完整记录能辨别不同脏工作树；历史记录不反推不存在的版本信息。（见 [design.md 决策 2](design.md#决策-2事实索引判断分别保存)、[决策 3](design.md#决策-3版本身份与可复现程度分别表达)、[决策 4](design.md#决策-4证据包有明确完整性与导入语义)）

### 子任务

- [ ] **一个完整 change：运行证据包的生成、校验与只读查看**。
  包含 run 启动身份、原始事件与轮次证据引用、结果完整性、导入幂等及 legacy 缺失说明。
  先覆盖 stdio 日常入口和对应 fake 集成夹具；其他入口标明未覆盖，不承诺所有历史数据可重建。
  不在本阶段增加 Web 控制面、真实模型批量运行或网络导出。

### 验收标准

- [ ] 同一 HEAD、不同有效 tracked/untracked 内容产生不同身份；执行者与目标仓库分别显示。
- [ ] 新任务可定位起始身份、工具/审批/验证与终态；一段恢复任务关联多 run，总量不重复计费。
- [ ] 可重建材料和仅有指纹明确区分；运行中实现漂移、缺指令正文分别显示原因。
- [ ] 同包导入两次计数不变；同 ID 异内容拒绝覆盖；断行/轮转/无终态/缺 artifact 不伪造完成。
- [ ] 路径穿越与符号链接逃逸被拒绝；查看证据不执行命令、不调用模型、不发网络请求。
- [ ] 采集失败不影响既有 Agent 结果、审批决定及 stdout 协议；显式导出失败有结构化错误。
- [ ] 固定性能夹具满足实施前锁定的门槛；关闭新增能力可回到既有行为。
- [ ] 行为测试先红后绿；全量 `./run_tests.sh -q`、适用 fake smoke 与文档检查有真实记录；Owner 按协作协议复核一个正常例和一个缺失例。

### 交付物

生产端证据协议、导出/校验/只读查看入口、兼容夹具、测试证据、限制清单与使用说明。
建议 change：`implement-build-agent-lab-p1`；本规划没有创建该 change，也未实现上述入口。

## P2 · SWE-bench 版本对照

### 前置条件

- [ ] P1 完成自动验证与相应人工 review，证据身份及完整性合同可用。
- [ ] 确定 SWE-bench variant（建议 Verified）、官方 dataset revision、预定 instance 清单和 split；小集合不得冒充全量。
- [ ] 核对现有 bench adapter、补丁收集、评分脚本和 CLI 入口在当前源码布局下可运行；锁定 Harbor、官方 swebench、镜像架构与 adapter 版本，不凭旧文档假定兼容。
- [ ] 明确从物化候选快照启动 Agent 的方法；独立固定版本的官方 grader 不随 A/B 候选变化；oracle preflight 与 Agent 输入隔离。
- [ ] 冻结原始/送评 patch 转换、缺预测、空预测、多次尝试、评分错误、分母、运行顺序和成本规则。
- [ ] 付费实验启动前确认模型、题数、重复次数和总预算；离线报告夹具可先验证，真实容器与模型结果另记。

### 目标

在固定 SWE-bench 题集与官方评分条件下比较两个 Agent 候选，逐题呈现 resolved、原生评分来源、过程证据及成本差异。
内部 eval 保留为快速自检，不替代主基准验收。（见 [design.md 决策 5](design.md#决策-5结果正确性由版本化独立评分决定)、[决策 6](design.md#决策-6对照实验先声明可比条件)、[决策 9](design.md#决策-9两个主基准复用原生执行与评分实验台管理证据和比较)）

### 子任务

- [ ] **一个完整 change：SWE-bench 实验从候选执行到官方评分的可比报告**。
  复用 Harbor 安装型 Agent、预测收集与官方 grader；补齐 profile、job/trial/run 映射、原始产物链、全部 attempt 及可比性验证。
  现有容器/评分链的必要适配属于该交付，不重写评分器；本阶段不增加 Terminal-Bench 专用规则或自动发布。

### 验收标准

- [ ] 固定报告夹具的改善/退步按 instance 正确展示；Agent 候选确实来自指定快照，用户随后修改原工作树不改变该实验。
- [ ] dataset/task 清单、镜像/环境、官方 grader、预算或 patch 转换发生非允许变化时给出 incomparable 原因。
- [ ] Harbor reward 与官方 grader resolved 分栏，二者冲突显示 score_disagreement；原生分数不能被实验台有效样本统计覆盖。
- [ ] 原始 patch 与送评 patch 都可校验；空/缺预测仍在清单中；新文件或转换遗漏不会静默丢弃；重复 instance 关联独立 attempt，不覆盖或挑最好一次。
- [ ] done 但独立检查失败判 fail；预算暂停不算通过；候选引起的构建/依赖/产物执行失败为 fail，评分设施故障为 invalid；故障归属不明时不作改善或采用结论。
- [ ] 缺题/无效结果保留预定分母与配对覆盖；候选让困难题变 invalid 不得显示总体改善；oracle 失败不能删题后宣称全量。
- [ ] 无价格时费用显示 unknown；重试、续做和失败成本保留；预算不足不启动新 attempt；容器授权仍经 ApprovalGate。
- [ ] 报告数值可追到官方 report 与原始日志；同包重复导入幂等；查询报告不运行 patch 或命令。
- [ ] 全量项目测试及离线集成通过；按授权预算完成至少一个固定小集合的真实容器/模型/官方评分对照，明确是 local_subset。尚未运行时只能标记工程验证通过。
- [ ] Owner 能指出实验变量、原生分母、一个失败及一个不可比原因；未获官方接纳时不得显示 accepted 或官方排名。

### 交付物

版本化 BenchmarkProfile、SWE-bench adapter/入口、原始与送评预测、官方评分报告、逐题对照及全部证据。
建议 change：`implement-build-agent-lab-p2`。完整 Verified 批次按预算另行运行，不是小集合验收的默认副作用。

## P3 · Terminal-Bench 版本对照

**阶段目标**：复用 Harbor 运行固定 Terminal-Bench 版本，将任务、trial、原生 verifier reward、轨迹、异常与成本完整关联到候选版本，并按该版本协议比较结果；这是第二个必需主基准。

**补细条件**：需要用户确定主版本与精确数据 revision、对应 Harbor 兼容性、资源/超时和重复试次要求，以及 P2 的共用证据映射反馈；随后写满前置、任务与验收，不预写未核实的 CLI 参数。小集合与全量分开，真实成本授权和正式上榜审核分别处理。

## P4 · 真实失败转回归

**阶段目标**：从真实失败形成带来源、固定初始状态和独立评分的案例，加入新题集版本，建立材料保留和本地备份。

**补细条件**：需要 P1/P2 实际证据缺口、首个重复出现的失败及其可重建环境；据此选择最小案例结构与开发/回归/保留集管理方式。

## P5 · 本地实验工作台

**阶段目标**：以配套本地 Web 应用串联运行时间线、版本对比、案例和实验结论，保留可核查来源。

**补细条件**：需要真实包规模、常见诊断路径和 P4 案例使用反馈，再决定独立仓库、框架、索引布局与交互性能门槛；不复制 Ink 控制面。

## P6 · 基线与回归门禁

**阶段目标**：建立可恢复基线、采用/拒绝决定及回归规则，使每次修改有明确比较对象和退步处理路径。

**补细条件**：需要多个固定协议实验的波动和成本数据、人工评分复核结果，以及实际运行频率，才能校准阈值、必跑题和 CI 预算。

## P7 · 可选观测集成与其他扩题

**阶段目标**：接入实际需要的其他评测源或观测后端，保持本地事实与比较协议完整。

**补细条件**：需要一个本地能力无法解决的真实场景和端点/隐私决定；逐个评估本地 coding、长任务 adapter 与 OTel/Langfuse/Phoenix；SWE-bench 和 Terminal-Bench 已归 P2/P3 主线。

## 阶段依赖与开发规范

`P1 → P2 → P3 → P4 → P5 → P6`；P7 由具体需求触发，必须先满足所需证据与协议合同。
远期顺序可依据真实反馈调整，调整要记录依据并重新评审受影响的范围与验收条件。

后续各 change 遵循项目 Spec → 失败测试 → 实现 → Review/mutation → 学习笔记的流程。
与当前 UX 工作共用代码时先检查工作树归属，保持每阶段可识别的 diff，不自动提交其他工作。
各阶段完成记录追加至 [task-log.md](task-log.md)，区分规划复核、工程验证、真实模型和人工验收。
