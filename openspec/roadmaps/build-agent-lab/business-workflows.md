# 从真实任务诊断出发重审实验台

> 2026-11-08，用户反馈驱动的设计增量。优先级已明确：**定位真实编码任务为何失败、反复或成本过高**。
> 这是对原型业务入口的修正；P1–P7 尚未实施，新增设计尚不代表原 v2 独立评审已覆盖。
> [原型记录](prototype-review.md) · [整体设计](design.md) · [业务术语](../../../CONTEXT.md)

## 1. 首版遗漏了什么

首版“实验记录 → 版本对比 → 任务证据”从已经得到评测结果开始。它能回答两份报告有什么不同，却无法帮助开发者从真实使用中的失败、反复和高消耗找到值得验证的改进。

用户的工作起点通常是：“这个任务没做好，我该改哪里？”这时可能没有第二个版本，没有已冻结的测试题，也没有足够证据判断是模型、提示词、harness、工具、环境还是人工干预造成。

因此下一版先验证以下旅程：

**发现任务异常 → 核对任务结果 → 定位关键请求/动作/上下文 → 区分事实与假设 → 整理最小改进及验证草案。**

版本、评测和回归继续承接后半程：冻结候选 → 机制/真实案例验证 → SWE-bench 与 Terminal-Bench 分别评估 → 采用或继续观察。双榜仍是主基准，不能覆盖所有交互、审批、恢复和成本问题。

## 2. 用本项目已有案例检验业务

| 实际场景 | 已有依据 | 实验台必须支持的判断 |
|---|---|---|
| Agent 说完成，但独立检查失败 | `20261023-113622/recall-guard` 报告中 agent_status=done；check 退出 1，符号链接逃逸检查失败 | 把 Agent 自述、执行终态、可见测试、独立评分分开；定位修复覆盖了格式校验但遗漏了哪项约束 |
| 计划只读任务因预算暂停 | P3 会话 `20261108-194449-131809`：规划 8,518 tokens，执行 22,520 tokens，验证命令未执行 | 关联规划与执行，展示每段预算和已知总消耗；预算保护生效、任务未完成分别表达，不把暂停一律判成模型故障 |
| 同题都通过，成本差异很大 | `20261025-143841/execution-chain` 三次 tokens 为 194,808 / 443,496 / 725,198，步数 11 / 24 / 36 | 同时看输入/输出消耗、调用与工具序列、上下文占用、重复读取和验证；3 次样本只作波动线索，不能证明某策略有效 |
| 更高分可能来自实验环境问题 | [本地编码基准](../../../docs/specs/local-coding-benchmark.md) 记录隐藏测试暴露、跑到外层仓库以及协议修正 | 标出评分可信度、工作区和暴露记录；保留成功产物但阻止过度归因 |
| 工具被拒绝后步骤仍被标完成 | [P3 证据驱动修复](../../changes/implement-improve-workbench-ux-p3/verification.md#证据驱动的修复) 记录该失败路径及红绿回归 | 查看审批决定、工具实际执行与步骤验收，建立确定性机制回归；外部榜单通过不能替代此检查 |

前三组已核对本地报告或验收摘要原文件；后两组作为历史文档线索，本轮未重新执行。历史记录中的旧模块路径、旧结论不作为当前源码事实。

## 3. 诊断的观察粒度

会话可包含多个用户任务；一个用户任务可能对应规划任务、执行任务和多段恢复。计划版本与实际执行段交叉关联，不能把所有记录简单按时间拼成一条 trace。

任务诊断页需要能逐层进入：

| 层次 | 要解释的问题 | 关键材料 |
|---|---|---|
| 用户目标与结果 | 用户究竟要求什么，哪些已经验证，哪些仍未知？ | 原始要求、验收约束、最终产物、独立检查、用户反馈 |
| 任务与运行段 | 卡在规划、执行、审批、暂停还是恢复？是否重复启动？ | task/parent、plan/version、segment/run、状态与边界事件 |
| 模型请求 | 该次请求产生了什么输出，消耗在哪里？ | request_id、模型与参数、输入/输出 usage、延迟、工具提议与可得的输出 |
| 工具与验证 | 动作被允许、被拒绝、执行失败还是成功？验证了哪个工作区？ | tool_call_id、审批、参数、cwd、结果、退出码、重试、文件差异 |
| 上下文变化 | 历史或工具输出是否膨胀？压缩前后发生什么？ | 请求前上下文组成、估算 token、内容指纹、压缩事件、实际可得正文 |

**已知采集边界**：`core/context/snapshot.py` 明确只保存计数、身份和来源。可展示上下文组成、变化与哈希，不能把这些称为精确的请求正文回放。会话末尾的消息也不自动等于某次调用的最终输入。

历史 P3 样本中 Task segment 的 run_id 与 trace 的 run_id 存在不同表示，不能仅靠相近时间宣称精确对应。原型应保留两种身份，明确标出映射未核实；P1 要解决生产端的显式关联。

## 4. 怎样避免诊断再次误导

- 每个诊断卡分开显示**已观察事实 / 可能解释 / 尚缺证据 / 下一步验证**。
- 重复的同名工具不自动等于浪费；相同参数也可能是修改后的必要复验。显示参数、先后顺序和文件/上下文变化供核对。
- token 是调用累计用量；请求前上下文占用是估算。输入累计占比高提示调查方向，不单独证明上下文策略有缺陷。
- 运行耗时、模型耗时、工具耗时和等待审批分别呈现；存在重叠或缺失时不强行加总。
- 预算停止与最终任务失败分别记录。预算可能在下一次请求前阻止调用，余额大于零不自动表示预算机制错误。
- `done`、独立检查通过、用户接受三个结论分开；用户拒绝动作不直接计为 Agent 能力失败。
- 缺失正文、价格、版本身份、调用关联明确展示；不能由模型编造归因。
- 改进草案引用具体证据与历史身份，不静默改写原始记录；同题调优后的表现不当作未见过题目的泛化证据。

## 5. 下一版原型范围

**入口：任务诊断。** 先展示“完成但未通过 / 预算中断 / 成功但代价波动”三个真实案例。案例来源分别标为本地模型评测或受控 Ink 真实验收，不冒充一般日常生产样本。

选择后可以：

1. 核对目标、执行状态、验证结论和资源消耗。
2. 展开运行、模型请求及工具记录，选择一条查看证据；按请求查看可得的上下文占用。
3. 查看重复动作和同题多次试次，区分可观察现象与原因假设。
4. 选择问题假设，编辑“拟改什么 / 怎样验证”，生成带证据引用的改进草案；仅在内存预演，不启动模型、写候选或运行评测。
5. 从诊断进入既有评测对比，保留双榜入口；正式版本冻结、任务调度和基线采用仍属于后续能力。

先不增加全量 Prompt 编辑器、自动根因判断、自动优化循环或通用项目管理。它们需要真实诊断旅程证明收益后再细化。

## 6. 业务验收

工程点击检查只证明按钮与数据关联可用。用户体验验收必须能完成这些判断：

- 指出 `recall-guard` 中“Agent 完成”和“独立检查失败”的差别，并定位失败依据。
- 解释预算样本停在哪个阶段，指出尚未执行的验证；不把重开查询当作续做成功。
- 在成本样本中指出一个值得调查的动作/上下文现象，并明确什么证据还不足以证明根因。
- 形成一个具体改进草案：来源任务、证据、假设、拟改层次、最小验证、防回归办法；无需先伪造第二个版本的成功结果。

后续实现顺序仍以 [路线图](roadmap.md) 为准。P1 的第一条真实验收应优先覆盖上述诊断场景及关联缺口；正式双榜接入仍按 P2/P3 承接，不能用离线原型代替。
