# P3：绑定所见版本的计划审阅与执行

状态：实施中，runtime 准确查询、Plan 写入保护与持久化启动/恢复已实现；既有 steering 已接线。新审阅 JSONL、TypeScript 协议/客户端与 Agent.run 交接已实现；Ink 准确审阅卡、焦点/草稿保护、正文分页与未知结果查询已接通。P2 代码/自动验证/工具 PTY 已通过，真人 Ghostty 验收待反馈；不把 P2 或 P3 标为验收完成。
来源：[路线图 P3](../../roadmaps/improve-workbench-ux/roadmap.md#p3--plan-审阅执行)、[设计决策 4](../../roadmaps/improve-workbench-ux/design.md#决策-4plan-审阅绑定版本批准并执行是一项可恢复操作)。

## 问题与结果

现在审阅时看到 A，审批命令却重新按产物修改时间选计划；“批准”和“执行”是两个请求，失败只返回文本，换请求 ID 重试会创建第二个任务。
目标是从一次性 `/plan <任务>` 得到可直接审阅的卡片，显式聚焦后一次确认“批准并执行”，始终操作所见对象；断线后可查回结果，批准成功但未启动时可从原对象继续。

## 行为约定

1. 卡片展示目标、步骤/验收摘要、版本与正文入口。草稿继续可编辑；裸字母不执行动作，聚焦、选择后 Enter 才确认。
2. 所有卡片动作绑定 session、原计划任务、plan_id、version 与内容 hash；新版本或内容变动使旧动作失效，不能切到另一个计划或旧 approved 版本。
3. 一份准确计划版本对应一次初始“批准并执行”操作。重复点击、重新打开卡片、请求 ID 改变及重连重试都查回同一任务；不会把再次执行藏进重试。
4. 明确区分未批准、已批准未启动、已创建任务、已启动/已结束、结果待核对。仅在证明从未开始执行时允许显式继续；存在启动证据时返回原任务及已有恢复入口。
5. 计划批准只决定该计划是否可执行，写文件和命令仍经过 ApprovalGate。busy、过期、stale、无任务运行时均有结构化结果。
6. 兼容现有管理命令与旧计划产物；新卡片不调用旧的“重新找最新计划”路径。普通命令默认选择语义不在本阶段重做。

## Module 与 Interface

`app/runtime/plan_review.py` 承担计划审阅 Module：查询一个审阅对象；对该对象执行显式动作。绑定、重复请求、任务分配和失败恢复留在其 Implementation 内。
stdio 只做传输和 Agent run 交接，Ink 只渲染结构化状态及发送用户意图。复用 Plan、TaskRuntime、TaskStore 和 StepLedger；不引入通用审阅平台或通用事务框架。
详细协议、持久化顺序和验证见 [design](design.md)、[tasks](tasks.md)、[预检与设计评审](verification.md)。

## 不在本阶段

反馈自动驱动只读修订（P4）、命令面重排（P5）、多会话导航/双向侧栏（P6/P8）、后台自动续跑、自动重放结果未知的工具动作，以及工具层“恰好执行一次”的承诺。

## 进入实现的证据
