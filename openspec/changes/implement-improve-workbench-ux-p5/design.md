# P5 设计：从意图找到可执行操作

## 启动时事实与接口

`protocol.ts` 混放静态命令目录与传输协议；`command-menu.tsx` 取描述，Composer 另取补全列表，App 的 help 长文本独立维护。Enter 当前提交原文，Tab 才接受候选。实际处理器还支持未列出的 attach/merge/stop-workers，以及大量 Plan 子命令。动态技能菜单在 `/skills` 时首项就是激活/卸载，需要明确保留列表动作。

在独立 `commands.ts` 集中命令、中文描述、分组、别名、用法与必填参数语义；菜单、填写决策与 help 共用。实际发送仍由 App 既有处理器完成，目录不获得额外执行权限。沿用已确认的 Composer/CommandMenu/App 输入 seam、BackendClient 命令与实际 Node→Python seam；终端尺寸和文件产物用于验证可见行为。

## 交互契约

- `/` 展示按任务/查看/设置组织的常用根命令；别名不重复占根菜单。中文搜索匹配意图和说明，英文前缀继续可用；子命令在所属前缀后发现。参数正文不当成新的搜索关键词。
- 菜单高亮候选时 Enter 接受该候选：必填参数缺失则填入命令前缀并提示用法，不发送占位文本；完整命令才交给既有处理器。Tab 始终只填充。无可见菜单时按原输入提交，但裸必填命令也必须提示参数并保留输入。
- `/chat <任务>`、`/act <任务>` 和反馈等要求输入正文；`/plan` 仍可审阅，`/autonomy` 仍可查看档位。直接输入的有效命令与别名保持兼容。`/skills` 默认明确选中列表动作，不能因新 Enter 规则激活首个技能。
- 选项接受后重新核对忙碌/断线/审批状态；未受理保留对应草稿，不能把菜单选择绕过 P1 gate。审批按钮焦点和修订反馈编辑不显示主命令菜单。
- 少于 18 行时隐藏菜单，Enter 只处理原输入；完整的裸参数命令仍提示填写，Tab 可先补全。无效或不完整的已知 Plan 子命令返回用法，不能回退为新的规划任务。
- `/help` 使用同一目录，`/help context` 等主题说明可查到用法与别名；`/tools` 应描述可用工具目录。动态技能说明仍由后端提供。

## 状态与后续切片

命令状态已接入菜单、所选项提示与提交复核；菜单保留不可用项并说明原因，Tab 可先填充，Enter 未受理时保留原输入。全局状态复用 Composer 禁止发送的条件。模式控制按下节使用独立请求，其余命令保持原运行边界。

| 当前状态 / 操作 | 提示与处理 |
|---|---|
| 启动、停止、等待审批、断线、计划/修订决策处理中、退出 | 说明对应原因，保留草稿；审批焦点仍只操作审批按钮 |
| 模型任务运行中的本地 help/context/copy/sidebar/project/about/theme/session、查看授权档位、查看/停止目标，以及 attach/merge/stop-workers/quit | 沿用现有处理器和各自对象校验；不把所有查看操作当成本地操作 |
| `/plan`、`/plan all` 只读审阅 | 运行中仍可查询；新后端使用独立 review 通道，旧后端读取已有产物；不替换当前运行或取消目标 |
| 后端 cost/diff/permissions/skills 等查询或设置、Plan 管理/执行、新任务 | 运行中先显示等待结束；提交再核对，未受理不清空 |
| `/followup` | 模型运行中可排队；工作台命令执行中提示稍后发送，resume 命令保留原有任务续做语义 |
| `/act`、`/chat`、带新需求的 `/plan` | 后端未启用 tasks 时提前说明；已有 Plan 子命令仍走其管理处理器 |

可用性这里只表达当前连接、运行和能力限制，具体计划是否可批准、任务是否可合并、参数是否合法仍由各自处理器与后端权威校验。回归曾发现把只读 review 错当成占用运行的查询，已恢复运行中只读查询并以 P3/P4 既有旅程验证。

## 当前运行与下一次默认模式

`task_state.mode` 只描述对应运行，`plan_mode` 描述下一条普通输入的默认值；两者分别显示，未知值不猜测。一次性 `/act`、`/chat` 不退出粘性 Plan。窄屏用「执行中 · 结束后规划」等短句保留当前与待生效关系，审批和审阅提示优先。

新后端的 `plan-mode-control` 允许 `/plan on|off|status` 独立于运行处理：不替换 active ID、不触碰审批与取消目标。运行中保存 wanted，结束时提交；反向选择原默认值撤回 pending。UI 不乐观修改模式，确认才清理对应旧输入，新草稿保持；超时可查询，迟到回执不覆盖新请求。旧后端沿用空闲命令路径。

重开时应用已保存的 pending 选择但不调用模型；说明会话已恢复、尚未运行和未发送草稿需重输。若提交默认模式失败，拒绝新普通任务并保留输入。显式任务仍按自身模式运行，不改 TaskRecord 的运行模式与工具边界。

## 紧凑主区

固定同一长文本与已装载上下文样本，80×24 基线正文只有 8 行。目标是无菜单/覆盖层时至少 12 行，同时保留三行草稿、上下文总量与分区摘要、详情入口及可见审批动作。

18–25 行窗口收起输入区上下留白，保持三行编辑；24–25 行的横向状态区只留一行上下文摘要，不重复运行状态和占用条。无上下文时不预留空状态行；头部会话信息、当前模式与页脚动作保持。更大窗口仍保留原有状态区，32×12 不改变原空间分配。上下文详情继续由 Ctrl+K 打开，菜单和审批按实际内容占行，不承诺始终有 12 行正文。

渲染快照与实际 PTY 都达到目标。正文选择/滚动位置沿用布局计算，按钮命中区域仍从实际渲染尺寸读取；三尺寸实际鼠标拒绝、草稿与恢复核验单独留证。Ghostty 真人理解程度与 Owner Review 待验收。

## 评审重点

避免 Enter 执行看不见的候选、中文任务被误匹配成命令、别名失效、动态技能误激活、裸 Plan 子命令退回成新规划任务、忙碌时清空草稿、状态提示抢占阅读。每次行为调整先固定失败测试，再纵向接通，最终全量测试与实际 PTY 分别留证。
