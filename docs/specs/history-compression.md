# W1 切片：history 分层压缩与 1M 分配

本页保留分层摘要与容量分配的初版记录。现行触发行为见 [自动压缩继续与交互可靠性](practical-use-reliability.md)：压缩后自动继续，同一 run 的总消耗不清零，默认总预算为 1M。

## 目标与原因

用户要求在本轮累计预算达到 80% 后，开始 history 滑动窗口与分层摘要，再进行一次进展收尾；同时合理分配配置的 1M 上下文容量。

原六分区总和为 384k，history 固定限制在 256k，不能借用空闲容量。这是容量管理上的限制，但原 MCP 任务停下的直接原因仍是累计 run 用量：多轮重复输入合计 208,401，超过默认 200k。扩大单次上下文可用容量不会减少这些重复输入。

## 容量账本

| 分区 | 默认 tokens |
|---|---:|
| system | 8,000 |
| memory | 64,000 |
| tools | 16,000 |
| history 名义额度 | 872,000 |
| 输出预留 | 32,000 |
| 安全余量 | 8,000 |
| 合计 | 1,000,000 |

采用原有 system/memory/tools 工程上限，把原先未分配容量归入 history，不采用等分。memory 是后续资料注入的容量，目前没有实现长期用户记忆；tools 仅指工具定义，工具结果属于 history。这些值是可调整的初始配置，不是普适最优比例。

默认 history 按实际余量计算：`window - output - scratch - actual_system - actual_memory - actual_tools`，因此最多可到 960k。显式 history cap 是额外硬限制，`unallocated` 记录留下的容量。状态显示本次有效额度，同时保留名义额度供核对。已有各分区超限告警仍保留。

`BudgetPolicy.for_context_window()` 统一默认值；`Config.budget_policy()` 构建应用策略。较小窗口同比缩放默认预留，显式超配的保留份额在工厂中缩减到窗口内。单次 run 的 200k 累计预算独立配置。

## 80% 后的行为

1. 进入 finalizing，不再发普通工具请求。首次长历史请求或下一次预估会耗尽余额时也触发。
2. 完整保留 system、原始目标和最新用户要求。近期窗口默认 8 组；assistant 工具调用与其结果作为完整组移动，保持先后关系。
3. 旧历史先写入 `.vibe/offload/`，按最多 8 组或约 8k tokens 分块提取 L1，再聚合为 L2（单个超大工具组仍完整处理）。近期组太大时缩窗，目标压到最多 8k history tokens，余额紧张时进一步缩小。即使余额耗尽，也保留至少 1k 的压缩目标用于下轮恢复；单请求容量更小时再取较小值。这不授权额外模型请求。
4. 原始目标和最新要求超过目标、或归档失败时保留原文并明确 over_budget。摘要保留可取回引用；已有 L2 没有新增旧历史时直接复用，有新增时合并，避免摘要标记和引用无限堆积。
5. 80% 压缩采用本地确定性提取，避免额外未计量模型调用。模型仅用压缩后的上下文执行一次无工具收尾；请求前重新检查余额。余额不足直接保存本地暂停说明。原文可供恢复后使用 `recall(ref)` 核对，提取摘要不承诺保留所有语义细节。
6. 原始日志保持追加。另存工作 history 快照及来源消息数量，恢复时应用最近有效快照和其后消息；坏快照忽略。`--continue` 打开 stopped run 不自动运行，`/resume` 显式开始新预算。

常规请求与收尾发送前均检查整条请求是否落在单请求输入容量内，固定目标超大时保存 `context_window` 暂停说明，不强行截断用户要求后继续请求。

即使完整响应一次越过累计上限，也会执行本地压缩、保存已生成内容、补齐未执行工具的协议结果；不会为收尾再调用模型。

常规窗口容量压缩仍使用原有可注入摘要器。本轮没有改变其预算计量路径；需要后续把该路径的模型摘要也纳入统一 usage，或统一改成本地提取。

## 工程依据

[Anthropic 的上下文工程说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)建议保留高信息密度上下文，压缩早期对话、保留近期工作信息，并通过文件引用按需取回原文。本文据此采用近期窗口、分层摘要和可取回归档；具体额度与 80% 触发点由本项目的使用反馈决定。

[官方 context engineering cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)区分对话压缩、工具结果清理与跨会话记忆。本轮仅处理会话工作上下文与原文归档，不把摘要当作用户长期偏好记忆。

## 验证

行为先补回归测试：1M 总账与借用、小窗口及环境配置、80% 单次收尾与压缩顺序、硬超限仍压缩、近期工具配对、分层摘要与复用、最新要求保留、原文跨实例取回、磁盘失败回退、工作快照恢复、TUI 持久化接线。使用 fake provider，不调用付费模型。

2026-10-20：完整测试 **206 项通过**；fake TUI 启动和退出通过。使用原 208,401 tokens 会话的副本离线压缩，history 估算 **33,473 → 8,000 tokens**，工作消息 **32 → 11**，近期窗口 **8 → 3 组**，4 个 L1 块聚合为 L2；跨 builder 取回 22 条归档消息，工作快照恢复一致。这个测试验证压缩、配对和恢复，不代表摘要语义完整性或真实 MCP 任务已验收。原会话未修改，产物仅在 `.vibe/smoke-history/`。
