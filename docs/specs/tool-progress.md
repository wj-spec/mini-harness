# 工具进展判断与降级

## 使用反馈与目标

用户反馈 `stopped: max_tool_calls`，明确要求工具调用次数不设硬上限，改为判断无进展、无效调用并降级。

原会话最后一次运行执行 50 次工具，累计 632,555 / 1,000,000 tokens，包含 1 次写入、4 次修改；46 组不同参数不支持将其直接认定为死循环。硬停止还留下 1 条未配对调用。独立 Fake 复现确认：60 次不同请求被第 51 次门槛截断，相同请求但结果递增也会在执行前被参数重复计数拦截。

## 调整

- 移除 max_tool_calls 与 max_repeats 及其旧环境变量读取。调用数保留作统计。
- 默认 max_steps=0，不用另一个 50 轮门槛替代原来的工具次数限制。显式 `--max-steps N` 和 eval 的任务轮数仍可使用。
- 任务总 tokens、费用、运行时长、各请求与工具超时、审批继续独立生效。

## 进展信号

`core.progress.ProgressMonitor` 是纯标准库的局部证据检测器，不依赖 TUI、HTTP 或模型自评。观察最近最多 128 个请求及完整输出摘要。

| 信号 | 行为 |
|---|---|
| 首次有效请求，或同一请求返回变化 | 清除连续停滞及纠偏阶段 |
| 重复不变结果，包含 A/B 请求循环 | 累计连续停滞 |
| 明确工具错误、bash 非零退出或超时 | 即使参数变化仍累计失败 |
| 只更新 plan/done/note | 不作为外部证据，不消除停滞 |
| 新成功写入或修改 | 清除修改前的读取、测试观察，允许验证重跑 |
| 相同写入重复 | 不无限重置进展状态 |
| 操作未获授权或被拒绝 | 立即反馈改用可行方法，同一动作不会再次自动申请审批 |

新输出是继续尝试的依据，不代表任务已完成。对不同文件的正常探索，即使内容一样也允许继续。bash 解析既有工具协议中的状态行，不扫描普通文件正文寻找 error 字样。语义层面“是否更接近用户目标”仍需真实任务验收；本轮使用保守、可解释的结构信号。

## 降级过程

默认 max_no_progress=2：连续 2 次停滞先纠偏，给模型一次调整方法的机会；调整后仍连续 2 次停滞才停止工具执行。新有效结果可以恢复正常阶段。设置 0 可关闭检测。

警告与停止都会中断当前批次中尚未执行的动作，为每个调用补齐 not_executed 工具结果。纠偏信息明确要求换方法、使用新的证据，拒绝后不重试或绕过权限。

持续停滞后，只允许一次无工具总结，说明已知信息、阻塞和未验证事项。空回复、截断、连接失败或模型再次提出工具都不续跑；余额或时间不足时仅保存本地说明。总结计入原任务用量，保留同一 run。停止使用 `stop_reason=no_progress`，不将其描述为“再给一轮预算即可”。TUI 引导补充信息或调整方法。

原文、压缩快照、取消、审批与工具配对规则保持。恢复旧的硬停止记录时，仍通过既有 interrupted 结果修复流程核对未执行调用，不自动补做动作。

## 验证

先补失败测试：超过 50 次有效调用、变化结果的轮询、无进展先纠偏、纠偏后恢复、不同参数失败、批次尾部不执行与配对、拒绝后不再弹审批、无工具总结禁用执行与异常不重试、TUI 区分阻塞与预算耗尽。core 单独验证缓存边界、A/B 循环、重跑测试、bash 状态和模型自报不能清停滞。

使用本地 Fake 验证，不调用真实模型或修改原会话。真实编码任务仍需使用验收。

## 2026-10-26 加固：重复读取与停滞警告预算

在原有“同参数结果重复/失败/仅更新计划”检测上补两类 harness 级护栏：

- **同一文件重复读取**：`read_file` 的 `path` 在两次成功修改（`write_file` / `edit_file` / `apply_patch`）之间累计读取超过 `max_reads_per_file`（默认 5）次，按 `repeated_read` 停滞处理。不同文件读取不受影响，修改成功后计数清零。
- **停滞警告预算**：`ProgressMonitor` 累计 `max_warnings`（默认 4）次停滞警告后直接 `stop`，即使中途出现新结果；避免“读一下新文件 → 再回到旧循环”的交替空转。
- **调用哈希**：对 `工具名 + canonical JSON 参数` 计数；同一哈希成功调用达到 `max_repeated_calls`（默认 6）即触发 `repeated_call`，即使每次输出不同，仍提示模型换参数/换方法。
- **真实进展（ArtifactProgress）**：动作任务中，工具调用累计 20 次（`max_calls_without_progress`）没有文件内容指纹变化或验证命令结果变化，先提示模型落到修改/验证；再一个窗口仍无进展则停止为 `no_progress`。文件指纹取自成功 `write_file`/`edit_file`/`apply_patch` 后的内容 hash；验证结果取自 `bash` 的 `verification=true` 执行状态/exit/output。QA/审查任务不启用，避免误伤只读调研。
- **工具状态引导**：`_tool_guidance()` 把 `tool_error` / 超时 / `duplicate_call` / `repeated_call` / `repeated_read` / `state_only` / 审批拒绝转成具体纠偏指令；普通首次错误也会在下一请求前注入“读错误、改参数、不要原样重试”；批量内完全相同的调用不会执行第二次。
- 阈值通过 `Config.max_reads_per_file` / `max_progress_warnings` / `max_repeated_calls` / `max_calls_without_progress` 暴露，对应 `VIBE_MAX_READS_PER_FILE` / `VIBE_MAX_PROGRESS_WARNINGS` / `VIBE_MAX_REPEATED_CALLS` / `VIBE_MAX_CALLS_WITHOUT_PROGRESS`，由 Ink、`run` 与 benchmark 共用。
- 仍保留原有停止边界：工具错误、审批拒绝、context_window、`max_run_seconds`、取消与错误；本轮不改变预算默认值。

测试：`tests/test_progress.py` 新增同文件不同范围读取、修改后重置、累计警告停止；`tests/test_config.py` 覆盖默认与 env；全量 Python 收集 925 项退出 0；TUI 305 项、304 通过（唯一失败为沙箱无 PTY 的既有项）。
