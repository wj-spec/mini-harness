# 建设方向

长期目标是一个越用越了解我的个人助手工作台。当前先发展 vibe coding 能力，在真实编码任务中积累使用反馈，同时理解 agent 的运行原理。阶段顺序表达建设重点，不预设完成日期或具体技术。

具体交付顺序、当前状态与完成条件见 [工作台里程碑 W0–W7](MILESTONES.md)；本页记录长期方向与取舍。

## 第一阶段：把单 Agent 编码流程用起来（当前）

对应 W0–W3：可复现起点、真实代码改动、运行中纠偏与停止、可靠续做同一任务。

已有基础包括模型流式调用、读写工具、执行命令、审批、上下文压缩、会话恢复、eval 和 stdio MCP 客户端（外部工具按配置挂载，走同一套审批）。具体实现与验收状态见 [README](../README.md) 和 [里程碑](MILESTONES.md)。

接下来围绕真实仓库任务，把需求、读代码、修改、验证和复盘串起来。每次只推进能够理解和验证的一小段，优先处理使用中反复出现的失败与摩擦。

这一阶段的判断标准是：能完成小型编码任务，能解释每一步由模型还是 harness 负责，并能通过测试和执行记录确认结果。新增能力应对应具体任务中的问题。

## 第二阶段：从使用反馈中积累个人上下文

对应 W4–W6：新任务复用项目背景、管理明确的个人偏好、验证个性化是否带来实际收益。

会话恢复和任务摘要已经服务于当前任务；它们还不等于长期了解用户。后续先观察哪些目标、偏好、项目背景需要反复提供，再决定哪些内容值得跨任务保留，以及如何查看、纠正和删除。

以重复说明减少、后续任务更贴合实际意图作为效果依据，再选择实现方式。本阶段尚未实现用户画像或长期记忆。

## 第三阶段：按实际需求扩展工作台

对应 W7：在出现明确的常用场景后，细化并交付第二种工作流。

在编码工作流稳定、个人上下文确有帮助之后，再根据反复出现的需求扩展到其他个人助手任务。TUI 是首个入口，长期界面由使用场景决定。

MCP、LSP、多 Agent、插件生态和其他界面，只有在当前工具无法解决的具体需求出现时再评估。stdio MCP 已能接入外部工具，但还没有在真实任务中验证过；HTTP transport、资源 / prompt 能力、LSP 与多 Agent 仍未实现。运行隔离也根据实际执行风险单独评估；当前命令边界仍是审批、黑名单和超时，不是系统沙箱。

## 持续取舍

- 先用真实任务发现问题，再决定功能与抽象；组件出现第二个实际使用者时再评估复用。
- 保持一个清楚的 Agent loop，让行为、审批和结果能够被解释与验证。
- 每次更新本文件时区分已有能力、当前工作和后续方向，避免把愿景写成已交付功能。
