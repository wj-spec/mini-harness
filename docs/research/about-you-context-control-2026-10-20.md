# “关于你”、上下文可见性与用户控制：研究笔记

日期：2026-10-20。用途：产品方向讨论依据，不代表已经实现或排入当前里程碑。

## 当前研究约束与重点

用户进一步明确：优先改善 Agent 运行过程的展示，避免为解释界面增加额外的模型生成。目标是通过已有目标、动作、结果和状态变化，使用户了解 Agent 的动向并找到干预位置。

- 展示由运行时确定性产生：事件、工具调用参数、审批决定、实际结果、时间、预算和上下文变化。
- 已有模型回复或计划可以直接展示，并标明它们的性质；不额外要求模型编写解释、规划或轨迹总结。
- 默认突出当前动作、关键变更、阻塞和失败，完整参数、输出和来源按需展开。
- “关于你”和上下文检查后续与执行轨迹关联；不把自动生成画像作为第一切片。

用户提到的 DSH profile 作为执行轨迹展示的方向参考；本笔记未检查其具体实现。

## 研究问题

当 Agent 根据用户偏好、画像、历史摘要和检索材料执行任务时，怎样让用户知道系统持有什么信息、哪些进入了当前请求，并能纠正不合适的输入？

本文把“理解债”作为产品讨论用语，不把它视为已有统一定义和量表的学术构念。需要区分两个问题：

- 对软件产物的理解：用户是否知道生成的功能与架构为什么成立、怎样修改和验证。
- 对 Agent 的理解：用户是否知道它依据了哪些目标、上下文、记忆和权限，可以在哪里干预。

“关于你”直接针对第二项；它能否改善第一项，仍需单独验证。

## 直接相关的原始依据

### 1. 可审查的用户模型：问题在 LLM 之前已经存在

Judy Kay，*Scrutability for Personalised Interfaces*，ERCIM News 46，2001。

- 文章把用户模型描述为系统持有的用户信念、偏好等显式表示；用户应能查看模型条目和形成它的来源、解释过程，并理解个性化如何发生。
- 这是作者的设计论述和系统工作介绍，不能当作“画像面板已经被实验证明降低理解债”。
- 对本项目的启发：重点应是“系统目前认为你怎样、凭什么”，而不是生成一段听起来准确的人格描述。

来源：[作者原文](https://www.ercim.eu/publication/Ercim_News/enw46/kay.html)。

作者还在[个人研究主页](https://jkay-github.github.io/)明确区分 scrutable 与 transparent：前者强调人主动审查所需的努力；不能把系统给出解释直接视为人已经理解。

延伸文献：Kay 与 Kummerfeld 的 [Creating Personalized Systems that People Can Scrutinize and Control](https://doi.org/10.1145/2395123.2395129)，TiiS 2(4)，Article 24。作者主页提供全文链接；本次出版商全文工具访问失败，不依赖其未核对的细节作结论。

### 2. 解释能改善可测量的理解，但证据范围需要保留

Brian Y. Lim、Anind K. Dey、Daniel Avrahami，CHI 2009。

- 211 人参加两项简单决策树系统实验。Why / Why-not 条件在部分客观预测、解释规则和心智模型指标上优于无解释条件。
- 实验二预测正确率为 Why 80.0%、Why-not 74.2%、无解释 61.7%；研究分别测量客观表现与自报理解、信任。
- 边界：短时、简单规则任务，研究者能产生对应规则的解释。作者也指出真实任务目标与复杂度不同；不能据此认定 LLM 的自述忠实，或长期 coding 能力提高。

来源：[Why and Why Not Explanations Improve the Intelligibility of Context-Aware Intelligent Systems，作者全文](https://www.cs.cmu.edu/~byl/publications/lim_chi09.pdf)。

对本项目的推论：可以用“用户能否预测下一次行为、定位错误假设”衡量理解，避免只问“你是否觉得更透明”。

### 3. 可编辑自然语言画像能成为实际输入控制，但效果不应只看面板

Jerome Ramos 等，*Transparent and Scrutable Recommendations Using Natural Language User Profiles*，2024，arXiv v2。

- 研究用自然语言偏好画像作为推荐输入；模拟编辑 200 位用户的画像，加入偏好后，对应特征推荐覆盖增加。
- 5 位参与者评价的是画像流畅、信息量、简洁和相关性，并非长期使用者的掌控感；负偏好编辑的下游变化较小。
- 作者指出画像会幻觉、冗长会增加负担。证据支持“输入画像可以成为行为调节面”，未证明用户可稳定纠正所有记忆，更未证明消除编码理解债。

来源：[作者论文全文，§5.3、§5.4、§7、附录 A.6](https://arxiv.org/html/2402.05810v2)。

对本项目的推论：要验证“关闭或修改后，下次实际请求和行为是否改变”，不能用“编辑按钮存在”替代控制有效性。

## 相关依据：解释、纠正和过度依赖

- Amershi 等，CHI 2019，[Guidelines for Human-AI Interaction](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)：49 位设计从业者对 20 种产品验证指南；涉及高效纠正、反馈后果、全局控制及变化通知。这是设计指南评估，不是 LLM 记忆降低理解债的因果试验。
- Buçinca 等，CSCW 2021，[To Trust or to Think](https://www.eecs.harvard.edu/~kgajos/papers/2021/bucinca21trust.pdf)：199 人实验中，认知促动可减少过度依赖，但伴随交互成本；不能直接推出记忆展示有效。
- Turpin 等，NeurIPS 2023，[Language Models Don’t Always Say What They Think](https://arxiv.org/abs/2305.04388)：在当时 GPT-3.5、Claude 1.0 的特定实验中，偏置信息能改变回答而不出现在解释中。支持“模型自述不能替代可核对的因果记录”，不能泛化为所有模型、所有解释。

## 现代 LLM 与编程 Agent 研究

### Semantic Commit：检查记忆冲突和接受修改应该分开

Vaithilingam 等，UIST 2025，[Semantic Commit: Helping Users Update Intent Specifications for AI Memory at Scale](https://arxiv.org/html/2504.09283v1)，[正式 DOI](https://doi.org/10.1145/3746059.3747778)。

12 人被试内研究，以各含 30 项内容的游戏设计文档、模拟财务助手记忆，对比 ChatGPT Canvas。局部检查、接受、拒绝和编辑让参与者更主动修改，主观控制更强；平均每任务 5 分 41 秒，对照 4 分 7 秒。5 人忽略了未标记冲突的部分，提醒我们冲突高亮也会引入依赖。自报认知负担没有显著差异，不能称为零负担。小样本、预置材料和短任务，不能推出长期代码理解改善。

本项目可借鉴的方向：展示新信息与现有记忆的关系后，让用户局部接受修改和撤销，而不是把整段自动改写的画像当作事实。

### Memolet：把记忆变成可以指定重用的对象

Yen 与 Zhao，UIST 2024，[Memolet: Reifying the Reuse of User-AI Conversational Memories](https://doi.org/10.1145/3654777.3676388)，[作者全文](https://www.jeffjianzhao.com/papers/memolet.pdf)。

12 人被试内、相隔一天的两阶段研究，涉及写作、编程、旅行规划。相较仿 ChatGPT 的检索、复制粘贴，抽取、组织并直接操纵记忆对象，改善了主观记忆理解与重用控制。参与者熟悉 AI，数据和时间有限；未证明长期画像更准确，也未测编码理解债。

本项目可借鉴的方向：用户可以选择本次使用哪条记忆、以何种范围使用，不能只有一页静态档案。

两项研究支持小规模可操作原型试验；都不足以承诺“关于你”消除 coding 理解债。

## 五个需要在产品中分开的对象

| 对象 | 回答的问题 | 可以承诺的范围 |
|---|---|---|
| 用户记忆 | 系统保存了哪些关于我的内容？ | 可定位的持久化条目及其状态 |
| 当前请求上下文 | 这一次发给模型的内容有哪些？ | 最终请求中的消息、工具定义及来源 |
| 任务解释 | 系统怎样概括这次目标和做法？ | 解释文本，可能需要用户纠正 |
| 执行记录 | 哪些动作确实发生了？ | 工具调用、审批、输出和副作用证据 |
| 软件交付说明 | 产物怎样工作，如何验证？ | 与代码、测试和行为相对应的说明 |

下面三句话不能混用：

1. “这条信息保存在系统中。”
2. “这条信息已加入本次请求。”
3. “这条信息导致模型做出这个决定。”

前两句可以通过存储、上下文组装和请求记录验证；第三句需要额外的因果证据。即使移除后行为改变，也应报告实验条件与随机性，避免声称找到唯一原因。

## 对 mini-harness 的产品假设

以下是本项目可尝试的设计，不是上述论文已验证的完整方案，也不自动改变当前开发顺序。

### 当前代码边界与第一步

当前代码没有个人长期记忆，`memory_cap` 是预算占位，[请求构建](../../app/agent.py)传给 `context.build` 的记忆用量为 0；已有的是内置指令、[启动时读取的 AGENTS](../../app/instructions.py)、TaskState、恢复历史、摘要和工具结果等任务上下文。

第一个小切片应优先整理已有执行事件，形成可展开的运行轨迹，再将本次上下文来源关联到对应请求。用户偏好和画像继续作为后续能力，当前里程碑顺序仍以 MILESTONES 为准。

### 零额外模型调用的执行展示

| 展示内容 | 可复用的数据 | 需要保留的语义 |
|---|---|---|
| 当前阶段 | 模型请求、审批等待、工具执行、压缩和终态事件 | 等待模型返回、等待用户审批、正在运行和已停止分别显示 |
| 执行动作与结果 | 工具名称、参数、调用 ID、输出和文件 diff | 工具请求、授权、开始执行和实际完成分别记录 |
| 目标与任务进展 | 用户原始输入、TaskState 的目标和计划快照 | 用户要求、模型提出的计划和运行验证结果标明来源 |
| 故障与恢复 | 错误、重试、超时、取消、未执行和结果未知事件 | 用实际事件展示，不由额外生成的解释补全未知结果 |
| 本次输入依据 | 最终 messages/tools 及压缩、offload 元数据 | 已发送的输入与模型自述的影响原因分别标识 |

代码入口：[TraceRecorder](../../app/trace.py)、[Agent.run](../../app/agent.py)、[TUI 回调与 trace 消费](../../app/tui.py)。现有记录包括模型请求起止、重试、预算、压缩、审批等待时长及 run 终态，但尚不是完整工具生命周期。

`TraceRecorder.tool_start/approval/tool_end` 虽有定义，当前主循环尚未调用它们；`on_tool` 在审批之前触发，不能将这一回调直接展示成“工具已执行”。可补充真实生命周期事件及稳定关联 ID，连接 run、模型轮次、工具调用、审批和结果。此处补的是程序事件，不增加模型调用。

未来子 Agent 只有实际发生委派时才增加对应轨迹，显示委派范围、输入和结果归属。先验证当前单 Agent 的读取、审批、写入、测试失败、修正和停止过程是否能被用户跟上。

AGENTS 当前仅在启动时读取，没有内容版本来源；摘要也没有细粒度来源链，这些是以后宣称可追溯时必须补上的边界。执行权限继续由 `ApprovalGate` 独立决定，画像偏好不能替代授权。

### A. “关于你”先做可纠正的事实清单

每条至少展示：

- 内容；来源是明确要求还是系统推断。
- 原始证据链接或会话定位；创建与最后确认时间。
- 适用范围：本次任务、当前项目或跨项目。
- 状态：候选、已确认、已停用、已过期；避免把推断写成永久事实。

适合的例子：“在当前项目，你要求行为变更先写测试。”

不适合无依据地泛化为：“你是一个永远偏好测试驱动开发的人。”

必要操作应有清楚语义：修改、停用、删除、仅限本项目、本次不用。

### B. 单独展示“本次带入了什么”

“关于你”不等于整个上下文。还需要展示当前目标、项目规则、近期对话、历史摘要、文件片段和工具结果。

- 默认显示来源和简短摘要；按需展开原文，不要求用户通读全部 token。
- 显示已加入与未加入的状态；未加入可以有预算不足、不相关或用户停用等原因。
- 上一轮加入不代表下一轮加入；每次请求应有自己的标识。
- 摘要和原始消息要区分，避免把有损概括当作原始证据。

工程建议：在最终 `provider.stream` 前捕获实际消息和工具定义。仅观察 `ContextBuilder` 的中间结果可能漏掉后续补入的纠偏指令或被替换的收尾请求，也无法对应每次重试。

UI 应写“已加入本次请求”，不要写“模型真正据此思考”或“决定原因”。如果 provider 还会序列化或注入内容，应标明快照覆盖到哪一层。

### C. 控制操作要能核对后果

- 停用记忆后，后续请求应不再从该条记忆注入内容。
- 如果同一内容仍在历史摘要或当前会话里，需要说明这些独立来源仍可能进入请求。
- 删除持久化条目不等于抹去已经发出的请求、工具副作用或外部服务日志。
- 修改要说明从哪个请求开始生效；执行中途不要暗示已经撤销之前的动作。
- 若未来有子 Agent，需要显示本次委派传递了哪些条目，不能假设主 Agent 页面覆盖了子 Agent 实际输入。

### D. 理解产物仍需要独立的一层

可控记忆解决“Agent 怎么认识我”，还应为重要代码变更保留“行为变化、关键取舍、验证方法、限制”的短交付说明。

用户不必理解每个实现细节，但需要能指出下一次修改的位置、一个可能失败的场景以及用来核对的证据。

## 怎样检验是否达到目标

先做少量可复现的任务，在相同初始条件的副本中比较普通流式日志与按真实事件组织的执行轨迹，检查用户能否判断当前动作、已发生变更、阻塞原因与停止边界。后续再单独评估上下文检查和记忆纠正，避免一次混入多种能力或让前一次执行的副作用影响后一次结果。

| 维度 | 可观察任务 |
|---|---|
| 知道系统持有什么 | 找出一条来源错误或过时的记忆 |
| 知道本次用了什么 | 区分已存储与实际加入的条目 |
| 能干预 | 停用错误偏好，并找到下次请求中的变化 |
| 会预测 | 解释某条项目偏好会改变哪些执行行为 |
| 不过度信任 | 在解释流畅但来源不充分时继续核对 |
| 成本可接受 | 记录完成上述操作耗时、打断次数和主观负担 |
| 理解软件产物 | 指出生成改动的验证方式和下一次修改入口 |

前几项改善、最后一项没有改善，也仍是有意义的局部结果；应按实际测量报告。

对“减少理解债”的表达宜保持为研究目标：当前依据支持可审查、可纠正、可验证的输入控制方向，尚不足以承诺长期能力不会退化。
