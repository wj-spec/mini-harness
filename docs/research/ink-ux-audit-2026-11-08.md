## 1. 结论

当前最值得投入的是 **减少误操作、让操作得到明确反馈、把已有结果接成可操作的流程**。
基础视觉设施已经不少：主题、分区、Markdown、多行编辑、历史滚动、复制、工具详情、审批层级、验收状态、Git 侧栏都已存在。
继续增加功能入口，会放大当前的命令负担和状态组合问题。

本次确定性探针复现了以下行为：

- 输入草稿期间弹出审批，随后单个 `s` 会直接提交 session 精确规则授权。
- Plan 模式提示与审批提示叠加时，80 列隐藏拒绝键，32 列隐藏全部审批键提示。
- 运行中输入 `/autonomy edits`，输入被清空，未发送命令，也没有拒绝原因。
- 回看历史时 `Ctrl+Y` 复制，阅读位置从历史跳回最新。
- `/followup` 排队后，前一任务以 `error` 结束，下一任务仍启动。
- `/co` 高亮候选后按 Enter，提交的是 `/co`，得到未知命令；裸 `/chat`、`/act`、`/help context` 也得到未知命令。

前四项有明确的局部修复方向；队列失败后的策略与菜单 Enter 语义属于需要明确产品约定的设计问题，不能仅凭探针判定现有实现违约。

## 3. 问题与目标交互

### U01 · P0 · 审批到达会改变正在输入的字符含义

**旅程**：任务执行中编辑纠偏草稿 → 工具请求审批 → 继续键入英文字符。

**发现（复现 + 源码）**：审批一到达就接管阅读焦点；`y/s/p/n` 单键立即响应，没有显式进入审批选择的动作。
探针先输入草稿，再发送审批事件，接着按 `s`，MockClient 收到 `decision=session`。
已有“忽略粘贴的 y”测试，但逐字键入是另一条路径。

证据：[审批单键处理](../../tui/src/app.tsx#L1222)、[审批状态接收](../../tui/src/view-state.ts#L210)、[输入焦点选择](../../tui/src/app.tsx#L1810)。

**建议**：审批出现时保留草稿，展示清楚的审批对象；通过明确切换焦点进入选项。
对 `s/p` 扩大授权范围的动作，先选择范围，再 Enter 确认；如保留快捷键，明确它何时生效。
这是修复字符被误解释，不改变 ApprovalGate 或放宽审批策略。

**验收**：逐字符输入、粘贴、按键重复与审批到达交错时，未明确进入审批操作就不会调用 approve；草稿保留。
正常键盘审批仍可完成，拒绝和取消始终可达。

### U02 · P0 · 状态前缀会把关键操作提示挤出屏幕

**旅程**：处在 Plan/Goal 等模式中 → 同时收到工具审批 → 找到拒绝或停止入口。

**发现（组合状态渲染复现）**：`hint` 先拼接 `planModeHint + goalHint`，再拼接当前面板动作，最后整体裁切。
虽然 `approvalHint` 自身会压缩，压缩时没有扣除模式前缀占用的宽度。
Plan active + 工具审批的合成状态在 80×24 末尾只到 `p…`，`n 拒绝` 与取消提示不见；32×12 仅剩计划模式说明。
这是组合状态探针，不代表已用真实模型走过相同序列。

证据：[hint 拼接](../../tui/src/app.tsx#L1764)、[整行裁切](../../tui/src/app.tsx#L1820)。

**建议**：按信息优先级分配空间：当前阻塞操作的确认/拒绝/取消优先，模式名只保留短徽标。
各面板只露出少量主要操作，其他动作进入 `? 更多操作`；不要把十几个快捷键拼成一行。

**验收**：32×12、80×24、120×40 下，审批所有可选范围和拒绝入口均可发现；开启 Plan/Goal、长任务标题后仍成立。
真正小于支持尺寸时只提供调整窗口和安全退出，不把截断文案当成合格交互。

### U03 · P0 · 忙碌时命令反馈不一致，部分操作静默消失

**旅程**：运行中希望降低授权档位、查看证据或调整配置。

**发现（复现 + 源码）**：`/autonomy` 分支先 `setInput('')`，随后发现非 idle 就直接 return。
探针确认 `/autonomy edits` 没有送到后端，草稿消失，界面也没有“未切换”提示。
部分其他命令保留输入但不提示，Plan/notifications 等则有明确忙碌提示；用户无法形成一致预期。

证据：[授权档位分支](../../tui/src/app.tsx#L1295)、[普通后端命令分支](../../tui/src/app.tsx#L1378)。

**建议**：对每条命令声明可用状态。忙碌时明确显示“本次未执行；任务结束后可用”，保留输入；能安全查询的视图允许查询。
需要排队的设置要显示待生效状态，并由后端确认，不能只改徽标。

**验收**：同一命令在 idle/running/stopping/waiting approval/closed 各状态下，均有可解释结果；不存在“输入消失但无请求、无提示”。

### U04 · P1 · 复制等轻操作会破坏历史阅读位置

**旅程**：向上回看输出 → 复制回复 → 继续阅读原位置。

**发现（复现）**：`copyCurrent → announce → notice` 最终强制 `follow=true`。
探针从“回看 · 下方 7 行”执行 `Ctrl+Y` 后变成“跟随最新”，视口从 130–137 行跳到 140–147 行。
它不是缺少滚动能力，而是反馈通知改变了阅读状态。

证据：[notice/announce](../../tui/src/app.tsx#L492)、[复制入口](../../tui/src/app.tsx#L1029)。

**建议**：复制成功、主题切换等轻反馈使用状态提示；写入历史可以保留，但不主动滚到底。
回看期间的新事件只增加“下方新内容”提示，发送新任务或显式回到最新再恢复跟随。

**验收**：键盘复制、拖选复制、设置反馈之后，原阅读锚点与焦点不变；失败提示可见。

### U05 · P1 · 命令菜单展示能力，但没有帮助用户完成意图

**发现（复现 + 源码）**：

- 44 个候选中包含别名和多项 sidebar/plan 子命令，最多显示 5 行，只按命令字符串前缀匹配。
- ↑↓ 高亮后 Enter 仍提交原输入；`/co` 会得到未知命令。测试明确锁定了这个行为，因此调整时需同时改变约定和测试。
- 菜单中的裸 `/chat`、`/act` 按 Enter 得到未知命令，而不是要求补充任务。
- `/help` 为长文本；`/help context` 不存在。`/tools` 菜单说明是“工具调用统计”，后端实际返回工具目录。
- 已实现的 `/attach`、`/merge`、`/stop-workers` 不在静态补全列表中。

证据：[命令目录与匹配](../../tui/src/protocol.ts#L20)、[Enter/Tab](../../tui/src/composer.tsx#L90)、[现有 Enter 测试](../../tui/tests/command-menu.test.tsx)、[help](../../tui/src/app.tsx#L1266)、[裸命令回退](../../tui/src/app.tsx#L1710)。

**建议**：将命令按任务、查看、设置分组；别名隐藏到说明中，子命令进入下一层；允许搜索中文意图与描述。
选中需要参数的命令后填入模板并进入参数输入，完整可执行命令才提交。Enter 的菜单行为与直接输入行为须明确区分。
帮助、补全、可用状态与参数提示共用一份命令描述，先覆盖实际命令，不必提前做插件命令框架。

**验收**：从 `/` 找到“查看改动”“续做任务”“调整授权”均不需要记英文命令；裸参数命令显示用法而非未知命令；帮助与真实处理器一致。

### U06 · P1 · 后续消息已能排队，但用户不能管理队列

**发现（复现 + 源码）**：`followups` 是内存字符串数组；提交后只有 notice，没有队列列表、撤回、编辑或调整顺序的入口。
当前 done 处理除 cancelled 外都会尝试启动下一条；探针复现前一任务 `error` 后继续启动后续任务。
断开会清空队列，取消会丢弃并告知数量；“纠偏”“后续消息”“后台计划任务队列”又是三类不同对象。

证据：[后续队列](../../tui/src/app.tsx#L264)、[启动逻辑](../../tui/src/app.tsx#L279)、[结束后的处理](../../tui/src/app.tsx#L453)、[followup 入口](../../tui/src/app.tsx#L1279)。

**建议**：输入框旁显示“发送为纠偏 / 排为下一任务”；提供“后续消息 2”入口，至少支持查看、编辑、撤回。
前一项错误、结果未知或验收失败时，建议暂停自动续发，让用户选择继续；独立任务可显式选择失败仍继续。
不要与 `/queue` 的后台计划队列混用名称。

**验收**：排两条后可撤回其中一条；错误后不会在没有可见策略的情况下自动开新任务；退出、断开与取消如何处理草稿/队列都有明确反馈。

### U07 · P1 · 权限的三个层次仍容易混淆

**发现（源码）**：已有 autonomy 档位、进程内精确/工作区授权、用户/项目策略规则。
但 `/permissions reset` 的菜单文案是“恢复默认审批规则”，后端只 clear 当前工作区的本进程授权，并不重置 autonomy 或持久策略。
`/permissions` 对进程精确规则只显示条数；工具 Entry 也没有承载自动放行来源的字段，常规工具卡无法直接解释为何没有询问。

证据：[菜单文案](../../tui/src/protocol.ts#L25)、[权限查询与 reset](../../app/stdio.py#L789)、[工具 Entry](../../tui/src/view-state.ts#L6)。

**建议**：最小修复是把 reset 改名为“撤销本进程授权”，执行后同时显示当前仍有效的档位与策略。
后续权限面板按“有效档位 / 临时授权 / 持久策略”列出范围、来源、存续时间；自动放行工具卡显示简短来源。
逐条撤销应走后端权威接口，不让 TUI 直接修改规则文件。

**验收**：用户能回答“为何这次没有问我”“授权何时失效”“撤销后还有什么会自动执行”；reset 不产生已恢复 ask 的误导。

### U08 · P1 · 完成、验证、改动仍需在多个入口拼起来

**旅程**：一轮结束 → 判断哪些文件改了 → 看验证失败 → 决定继续修复。

**发现（源码）**：已验证/待验证状态已有，但下一步主要是 `/evidence`、`/diff`、`/resume` 命令提示。
`/evidence` 是最近一轮的文本摘要，包含原始字段/原因码；Git 侧栏对比的是当前工作区与 HEAD，不能直接等同于“本轮改动”。
工具卡、回执、diff、计划验收之间没有稳定的同一轮导航。

证据：[结果状态](../../tui/src/agent-status.tsx#L15)、[证据格式化](../../app/session/evidence.py)、[回执卡呈现](../../tui/src/workbench.tsx#L63)、[侧栏 diff 范围](../../tui/src/sidebar/git.ts#L73)。

**建议**：回执卡先回答“本轮改了什么 / 哪些验证通过 / 剩余阻塞是什么”，再提供可聚焦动作：查看改动、查看验证、带失败上下文继续。
绑定明确的 run/round；完整 hash、原因码与审计字段放详情。
“带失败继续”若需补后端上下文绑定，应单独列依赖，不承诺只是换卡片。

**验收**：在 80×24 中无需手输命令即可从回执进入失败验证与相关文件；旧任务继续失败验证时不会错误绑定最新一轮。
工作区 diff 清楚标示范围，不把用户已有改动归为 Agent 本轮修改。

### U09 · P1 · 会话、任务、后台审批缺少对象选择与连续操作

**发现（源码）**：`/tasks` 与 `/approvals` 返回文本；审批收件箱最后提示转去 attach 或 CLI。
`/attach now` 已有快捷路径，但任务列表无法选中某任务后直接调用；旧会话仍通过 `--list-sessions → --session ID` 打开。
这些入口的后端能力已存在，不需要先引入新调度器。

证据：[任务与审批文本](../../app/stdio.py#L155)、[attach](../../tui/src/app.tsx#L1320)、[会话入口](../../tui/src/cli.tsx#L23)。

**建议**：先做当前会话任务选择器，显示目标、运行状态、等待原因、待审批数和更新时间，再按状态提供查看/attach/停止等动作。
后台审批可从任务进入现有 attach 审阅通道；直接跨任务审批需新增权威协议，不能仅由前端拼出批准。
会话选择器作为后续切片，选中先预览进度，再显式续做。

**验收**：找到等待审批的任务不需要复制 ID 到 shell；已结束、过期、无 worker 的任务给出不同动作；打开旧会话不自动运行。

### U10 · P1 · 紧凑布局需要按任务优先级分配空间

**发现（渲染 + 源码）**：80×24 普通布局正文可见 8 行；输入 `/` 后菜单占 5 行，正文只剩 3 行。
状态重复出现在 Header、紧凑状态区、页脚，输入区空白时也保留固定高度；120×40 另有固定 32 列状态面板。
它们都没有越界，但“没有越界”不足以保证阅读效率。首屏示例是静态文本，不能直接选中填入。

证据：[行数分配](../../tui/src/app.tsx#L313)、[欢迎页](../../tui/src/workbench.tsx#L111)、[Header/StatusPanel](../../tui/src/agent-status.tsx)。

**建议**：窄屏默认收起重复状态与空行，输入框按内容增高；仅保留“当前阶段、是否等我、怎样停止”，预算详细分区按需展开。
长等待显示已等待时长、最后事件时间；只有后端提供真实重试/超时信息时才显示，不伪造百分比。
示例任务可用键盘填入草稿，用户确认后再提交。

**验收**：在相同 80×24 场景提高正文可见行数，同时保留停止、审批和预算风险提示；用户不必开详情就能区分等模型、等工具、等自己。
具体行数目标先用实际终端比对确定，不把“信息越多”作为验收标准。

### U11 · P2 · 长会话需要定位工具，不止能滚动

**发现（源码）**：已有全文记录和工具详情，但主对话没有文本搜索、按轮跳转或按类筛选；每条工具记录都会形成卡片。
读很多文件的任务，会把较少的结论与决策淹没在工具卡中。不能据此宣称存在性能瓶颈，本次没有测长会话延迟。

证据：[逐 Entry 渲染](../../tui/src/workbench.tsx#L86)、[工具选择键路](../../tui/src/app.tsx#L1241)。

**建议**：先做本地文本搜索和跳到上一轮/上一次错误；再折叠连续成功的只读工具调用，保留展开入口与原始记录。
失败、审批、文件修改和结果未知项默认展开。搜索、展开、复制均保持阅读锚点。

**验收**：在几百条记录中能定位旧报错和旧结论；折叠不删除执行证据；搜索不会触发模型调用。
