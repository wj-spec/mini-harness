# 任务预算与上下文预算“撞车”排查

日期：2026-10-25。结论：暂停是**累计任务预算**（`max_run_tokens`）耗尽，不是 1M 上下文窗口被占满。默认值恰好都是 1M，加上接近预算时上下文被压缩，放大了“两个预算撞车”的观感。

## 现象

截图中一次代码审查任务在 `status=stopped, stop_reason=token_budget` 暂停：

- 任务累计 Tokens **999.8k / 1M**；
- 当前上下文估算仅 **11.4k / 960k**；
- 上下文容量、输入剩余均接近满额，说明单次请求远未超限；
- 会话文件：`.vibe/sessions/20261025-223846-073371/`（本地运行产物，不提交）。

## 运行证据

同一会话连续 3 次 run（用户两次 `/resume`）：

| run | 步数 | 累计 Tokens | 上下文峰值 | 结束时上下文 | 停止原因 |
|---|---:|---:|---:|---:|---|
| `505adbc2` | 46 | 995,372 | 35,045 | 14,904 | token_budget |
| `69f77cd0` | 46 | 999,822 | 29,338 | 11,369 | token_budget |
| `f7973d1e` | 46 | 997,533 | 26,752 | 13,090 | token_budget |

- 上下文峰值只有 26k–35k，远低于 960k 请求容量；
- 3 段共消耗约 3M tokens，仍未完成审查任务；
- 每次 run 约 8 次 `history_compacted`；末段压缩目标出现 **0**、**1024**、**1895** tokens：
  - `request_budget`：before 11,243 / after 11,243 / target 0
  - `task_budget`：before 11,243 / after 7,078 / target 8000
  - `task_budget`：before 7,541 / after 1,895 / target 1895

## 原因链

1. `app/config.py` 默认 `max_run_tokens = 1_000_000`，而 `context_window` 也是 1M。前者是**一次 run 内所有请求的输入+输出累计**，后者是**单次请求容量**；两者独立，但默认数值相同，用户自然会把“任务预算”误读成“上下文预算”。
2. 46 步 × 平均约 21k 请求，累计约 1M；即使每步上下文很小，累计预算也会先耗尽。`Agent._decide_after_model` 在 `token_exhausted` 时进入 `_pause_budget`，这是当前预算语义下的预期行为。
3. 更关键的是 **`_automatic_history_target` 用“剩余累计任务预算”反推 history 目标**：剩余预算越少，压缩目标越小（甚至 0/1.9k）。于是任务预算在耗尽前不断挤压上下文，既浪费一次压缩，也让最后几步在极小上下文里工作。
4. 暂停后必须显式 `/resume` 开新一轮预算；3 段各 1M 后仍未完成，用户需要反复恢复，体验上像“任务被卡死”。

## 方案

### 立即缓解（不改代码）

为长任务调大累计预算，或关闭累计预算：

```bash
VIBE_MAX_RUN_TOKENS=5000000 ./run_ink.sh   # 或 0 = 不限
```

单请求上下文仍由 `VIBE_CONTEXT_WINDOW`（默认 1M）限制；`max_run_seconds`（默认 600s）仍兜底。代价是成本上升，需要配合 `/cost` 观察。

### 推荐修复

1. **明确语义与默认值**：把 `max_run_tokens` 标注为“任务累计预算（所有请求之和）”，与“当前上下文（单次请求）”分开展示；默认值不再与上下文窗口相同（建议 0=不限，或更高的显式值），成本控制交给 `VIBE_MAX_RUN_COST_USD` / 秒数 / 可选累计预算。
2. **停止用累计预算压缩上下文**：`_automatic_history_target` 只按上下文容量与固定保留计算；设置 history floor（如 8k），不允许 `task_budget` 把上下文压到 1k 级别。若剩余累计预算不足以容纳一次最小请求，直接暂停并说明“预算不足”，不再做无意义压缩。
3. **分段预算 / 可选自动续做**：把 `max_run_tokens` 定义为单段预算，另设总上限（默认 0）；每段结束自动 checkpoint，按配置自动开下一段（需显式开启，防止无限花费）。暂停 UI 显示“第 N 段已用完”，而不是让用户手动反复 `/resume`。
4. **UI 可解释性**：状态栏同时显示 `任务累计 999.8k/1M（所有请求）` 与 `当前上下文 11.4k/960k（单次请求）`；达到 80%/95% 时提示；暂停时给出 `/resume` 开新段与调整预算的命令。

### 建议顺序

先做 1+2（低风险、直接消除上下文被挤压和默认值误导），观察真实任务；如果仍有跨 1M 的长任务，再做 3（自动续做需产品确认成本策略）。

## 验收要点

- fake provider 连续请求：默认配置下不再因“任务累计≈1M”出现 `task_budget` 压缩到 0/1k；
- 设置硬预算时，暂停前最后一次上下文目标不低于 floor，且 `stop_reason=token_budget` 可解释；
- TUI 标签能区分两种预算；`/resume` 显示段计数（若做 3）；
- 现有预算测试（`./run_eval.sh check-budget`、`tests/test_agent_budget.py`）保持通过或按新语义更新。
